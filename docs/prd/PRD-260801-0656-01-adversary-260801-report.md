#### B3 — fired

##### What makes a second unnamed `launch` eligible to tile?

- **hunt:** B3
- **impact:** Repeated valid `launch --cmd ...` invocations without `--name` can retain the compounding 30:70 behavior indefinitely, so the advertised tiled default for `launch` and the end-to-end path past the third pane are not delivered for that public invocation shape.
- **evidence:** The PRD promises, “a flagless `launch` or `spawn-agent` … will tile instead” and says the first placement makes the window eligible so “the second and later spawns tile” (`PRD-260801-0656-01`, lines 71–82). But the same PRD says an unnamed, agentless `launch` pane has neither `@tt-name` nor `@tt-agent`, “so it is not ‘ours’ under the shared predicate — for layout as for `kill`,” and explicitly leaves making it owned out of scope (lines 405–419 and 621–632). The tile brief only accepts a second placement into “a window this tool already owns” (`ISSUE-260802-0128-01`, lines 98–108), while ISSUE-260801-1310-02 also puts “Making unnamed, agentless `launch` panes owned” out of scope (lines 87–93). The live code confirms the persistent state behind the collision: `src/cmd/launch.rs::run` sets `@tt-name` only when `--name` is present, then only `@tt-launched-at` and `@tt-cwd` (lines 101–107), whereas `src/cmd/spawn_agent.rs::run` unconditionally sets `@tt-agent` (lines 81–93). No brief owns the unnamed-`launch` path between those facts and the promised default.

#### B4 — fired

##### Can one ownership boolean preserve both safety denial causes without restating ownership?

- **hunt:** B4
- **impact:** Implementing ISSUE-260801-1310-02 literally loses the distinction between an unregistered pane and a registered pane from another cwd, or leaves duplicate ownership logic in the binary; either outcome violates an explicit acceptance condition.
- **evidence:** The brief defines `pane_is_owned` as taking a registration plus optional cwd and “return[ing] whether the pane is owned,” while requiring the safety evaluator to keep “its two distinct denial messages” and forbidding any equivalent field-presence test from surviving in `src/` (`ISSUE-260801-1310-02`, lines 41–49 and 59–81). In the repo, those messages arise from two different branches: `src/cmd/safety.rs::evaluate` first computes `name.is_some() || agent.is_some()` and emits “not created by tmux-tools” when false (lines 56–63), then separately checks cwd only for a registered pane and emits “owned by another cwd” on mismatch (lines 65–76). Both failures collapse to the same not-owned result at the proposed predicate seam, and the current evaluator has no other source for which message to choose.

##### Is the current shared launch seam large enough to become the promised `split → register → measure` operation?

- **hunt:** B4
- **impact:** ISSUE-260801-1310-04 can move the shared split code yet still leave registration outside the layout operation, making its fixed ordering and later slices' assumed seam false even though the issue's listed CLI-output criteria pass.
- **evidence:** The brief says the core module performs “**split → register → measure**” and describes its surface as “target + incoming agent identity → landing report” (`ISSUE-260801-1310-04`, lines 29–52 and 60–65). The actual common chokepoint stops at pane creation: both verbs call `src/cmd/launch.rs::launch_pane`, which accepts command/layout/target data and even discards its `name` parameter (`launch.rs`, lines 172–223). Registration happens afterwards in two separate binary-verb blocks: `launch::run` writes optional name, launch time, and cwd (lines 99–107), while `spawn_agent::run` additionally writes agent and access (lines 81–93); both obtain the launch timestamp from binary-only `src/util.rs::rfc3339_utc_now`. Thus the repo has a shared split/layout seam, but not the shared registration seam the issue says can move wholesale, and the stated placement input does not carry the registration data the operation promises to write.

##### Can target-pane safety supply the window-level ownership guard used after `kill --any`?

- **hunt:** B4
- **impact:** In a marked mixed window where the killed pane is unowned but a surviving sibling is owned, retiling can be incorrectly skipped or incorrectly authorized; the breakdown has no observable that disambiguates the two scopes.
- **evidence:** ISSUE-260801-1310-06 says the layout guard is window-level — “The window must contain a pane owned by this invocation” — but then calls the existing safety evaluation “the natural place to capture the ownership answer before destruction” (lines 31–48 and 61–66). The repo's safety seam is only target-pane-level: `src/cmd/safety.rs::enforce_for_pane` reads registration for one `pane` and returns that `Registered` value (lines 90–110), and `src/cmd/kill.rs::run` invokes it for the target immediately before `kill-pane` (lines 35–40). It neither identifies the containing window nor enumerates sibling panes. The issue criteria cover a target carrying the window's only ownership evidence and a wholly foreign window under `--any`, but not an unowned target in a window owned through a different pane (`ISSUE-260801-1310-06`, acceptance criteria).
