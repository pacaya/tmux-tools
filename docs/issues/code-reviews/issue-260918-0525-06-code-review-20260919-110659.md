### H1. Alternate-screen output can be silently labelled complete (FIXED)

### M1. Alternate-screen result includes all pre-submission main-screen history (FIXED)

**Source:** CLAUDE-1; Codex agrees.
**Files:** `src/cmd/prompt.rs:442`

When the pane is on the alternate screen, `extract_result` starts at line 0 of `capture-pane -S -`. tmux keeps the main-screen history while the alternate screen is on, so the result carries up to `history-limit` lines from before submission. **Required outcome:** On the alternate screen, start the result at the visible screen (`history_size` of the settle probe). Add a CLI test in which distinctive pre-alternate output is absent from the result and the echo is present.

### L1. Session is visible before its history limit is set, and the limit is targeted by name (FIXED)

> **Fix:** Managed-session lookups use exact `=tmux-tools`/`=tmux-tools:` targets; the private session is `tt-pending-<pid>-<nanos>`, its limit is set by `#{session_id}`, and the command's window is created by that id; CLI tests cover a caller TMUX context and a stray `tmux-tools-pending-*` session (both reviewers verified after batch 3).

**Source:** CODEX-2; Claude agrees.
**Files:** `src/cmd/launch.rs:214-217`, `src/cmd/launch.rs:303-313`

Creating the session and setting its `history-limit` are separate tmux invocations. A concurrent `launch` can see the new session, take the not-created path, and open its pane before the limit is set. Because the option is targeted by session name, a same-named session recreated in between would receive it even though this operation did not create that session.

**Required outcome:** Create the session and set its `history-limit` in one tmux command sequence so no other client can interleave (for example `new-session … \; set-option …` in one invocation). Target the created session by its stable `#{session_id}`, not its name.

**Recheck after correction batch 1 (STILL_BROKEN; treated as HIGH impact):** batch 1 creates the session with `new-session -d -s tmux-tools \; set-option history-limit 50000`, and the `set-option` has no `-t` (`src/cmd/launch.rs:295-305`). `new-session -d` does not bind the command queue's current target, so the untargeted `set-option` resolves against the caller's context. The orchestrator reproduced this on an isolated tmux 3.7c server. With `TMUX`/`TMUX_PANE` pointing at a pre-existing `caller` session (limit 777), the sequence left `caller` at **50000** and the created `tmux-tools` session at the global **2000**. A real `launch` run from inside tmux takes the calling-pane path (`src/cmd/launch.rs:196`) and never reaches session creation. The defect is that the option's destination depends on the tmux client's resolution context rather than the created session's identity. Adding `-t =tmux-tools` to `set-option` inside the same sequence fails on 3.7c with `no such session`, because the target is resolved before `new-session` runs. Codex also notes that an `after-new-session` hook runs before the untargeted `set-option`.

**Required outcome (updated):** `history-limit` 50000 lands on the session this operation created and nowhere else, whether or not the caller's environment carries `TMUX`/`TMUX_PANE`. It lands before the launched command can emit output, and no concurrent client can open a pane in the new session under the old limit. Add an isolated-server CLI test that runs `launch` (and `spawn-agent` if it takes a different path) with `TMUX`/`TMUX_PANE` pointing at a pre-existing session on the test server, pinned to that server's socket. Assert that the pre-existing session's `history-limit` is unchanged, that the created session's effective `#{history_limit}` is 50000, and that the first-line retention criterion holds.

**Recheck after correction batch 2 (STILL_BROKEN; both reviewers):** batch 2 creates a private session `tmux-tools-pending-<pid>-<nanos>`, sets the limit by `#{session_id}`, then renames it to `tmux-tools`. The private name starts with the managed name, and tmux resolves `-t tmux-tools` by prefix when no exact match exists. On an isolated tmux 3.7c server with only a pending session present, `has-session -t tmux-tools` succeeded. `launch --cmd "sleep 60" --bare` then opened its pane in the pending session at history-limit 2000 and never created `tmux-tools`. So a concurrent launch adopts another caller's unpublished session under the old limit. A leaked pending session captures every later launch, and two pending sessions make the lookup fail as ambiguous. The stable id is also dropped after the rename: `launch_pane` targets `tmux-tools:` by name in a separate call, so a kill-and-recreate in between can put the command in a replacement session.

**Required outcome (batch 3):** Resolve the managed session only by exact name (`=tmux-tools`, `=tmux-tools:`) in every lookup in `src/cmd/launch.rs` and `core/src/target.rs`. Give the private session a name that does not start with `tmux-tools`. Have session creation return the created or adopted session's `#{session_id}`, and create the command's window by that id. Add an isolated-server CLI test: with a stray `tmux-tools-pending-*` session and no managed session present, `launch` creates `tmux-tools` and its pane's `#{history_limit}` is 50000.

### L6. Pending session leaks when a post-creation tmux invocation errors (FIXED)
