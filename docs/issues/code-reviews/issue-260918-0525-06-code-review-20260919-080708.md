### H1. PREMISE_CHANGED: P7's eviction predicate misses tmux's batched history collection

**Source:** CLAUDE-2; the orchestrator verified it directly on tmux 3.7c.
**Files:** `src/cmd/prompt.rs:64-69`, `src/cmd/prompt.rs:358-362`

P7 fixes the eviction predicate as `history_size + visible_rows >= history_limit`. When `hsize` reaches `hlimit`, tmux drops `hlimit/10` lines at once, so `history_size` saws between roughly 0.9×limit and the limit.

Probe: a pane with history-limit 1000 and 82 rows, after printing 1090 lines, reported `history_size` 909, and the capture began at `line101`. 909 + 82 = 991 < 1000, so the predicate reports complete while 100 lines have been evicted. At the mandated 50000 limit the 5000-line batch far exceeds the visible rows, so an evicting pane is reported complete for most of its cycle. `result_from_mark` then slices by a mark offset that eviction has shifted, which skips the start of the turn under `complete: true`.

**Required outcome:** Maintainer decision on the P7 eviction predicate, for example "incomplete when post-settle `history_size` < mark, or when `history_size + visible_rows >= history_limit - max(1, history_limit/10)`", or a monotonic eviction signal. Then refresh the requirement and approval. The implementation must not return a mark-offset slice labelled complete after any eviction since the mark.

### H2. PREMISE_CHANGED: `history-limit` is session-scoped, so "set on each pane at creation" cannot hold per pane

**Source:** CODEX-1; the orchestrator verified it directly on tmux 3.7c.
**Files:** `src/cmd/launch.rs:235-243`, `tests/integration.rs:4553-4581`

Probe: two panes in one session, session value 1000. `set-option -p -t <pane2> history-limit 50000` set the session value to 50000, and `#{history_limit}` became 50000 on both panes. The per-pane setting leaks to every sibling in the session. The `show-options -p` oracle named by the acceptance criterion therefore does not show pane isolation, and on older tmux the change does not resize an already-created grid.

**Required outcome:** Maintainer decision on the P7 creation clause and its acceptance oracle. Options include a session-wide limit set before creation, or giving created panes their own session. Then refresh the requirement and approval. Tests should check that output is actually retained and what happens to an existing sibling pane, not rely on `show-options -p`.

### H3. `prompt` still settles on `Unknown` as idle when the resolved surface supplies patterns

**Source:** CLAUDE-1, CODEX-3 (both reviewers agree; confirmed in code)
**Files:** `core/src/idle.rs:252-270`, `src/cmd/prompt.rs:118-125`, `src/cmd/prompt.rs:157`

The brief allows idle detection only when the resolved surface supplies no patterns or the pane resolves to no surface: "otherwise unknown is never treated as idle". `wait_for_idle`, which `prompt` shares with `wait-idle`, returns `IdleReason::Idle` for any quiet `PaneState::Unknown`. That includes a patterned surface whose capture matches neither pattern or both. `prompt` can therefore return mid-turn with partial output.

**Required outcome:** For `prompt` only, disable the quiet-idle fallback when the resolved surface has patterns; `wait-idle` keeps its current behavior. Add CLI tests with `tt-fake-tui` that hold the neither-match and both-match Unknown states past `idle_seconds`, and assert that `prompt` does not settle with reason idle.

### H4. `history-limit` is applied only after the child can already emit output

**Source:** CODEX-2 (Claude did not cover it)
**Files:** `src/cmd/launch.rs:218-226`

`split-window`/`new-window` start the child before returning the pane id, and the limit is raised afterwards. A fast child can exceed the old limit first, and those lines are lost for good. The raised limit then makes the completeness predicate report complete. This breaks the "at creation" clause.

**Required outcome:** Resolve this together with H2. Set the limit before the child can emit output, and add a CLI test whose child immediately prints more than the prior limit and asserts its earliest line is still available.

### M1. The history mark is taken at the top of the pre-submission screen, not at the submission point

**Source:** CLAUDE-3 (Codex did not cover it)
**Files:** `src/cmd/prompt.rs:127-131`, `src/cmd/prompt.rs:298-310`

The mark is `#{history_size}` alone. The result therefore includes the whole pre-submission visible screen (up to `pane_height` rows) of the previous turn's output. The tests assert only `contains(...)`.

**Required outcome:** Take the mark at the pre-submission cursor row (`history_size + cursor_y`, read in one invocation), so the result starts at the submission line and still includes the echo. Add a CLI test that puts distinctive prior output on screen and asserts it is absent from the result.
